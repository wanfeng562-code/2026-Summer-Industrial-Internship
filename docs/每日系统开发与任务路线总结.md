## 1. 项目目标与课程主线

课程项目是 **AI 智能客服工单处理系统**。目标不是单纯完成“工单 CRUD”，而是形成三类用户参与的完整服务闭环：

```text
普通用户：登录 -> AI 咨询 -> 创建/补充工单 -> 查看处理进度 -> 问题解决/关闭
客服坐席：登录 -> 查看待人工工单 -> 接单/回复 -> 更新工单状态 -> 完成处理
管理员：管理账号、坐席/策略/知识库 -> 督办与统计 -> 优化服务流程
```

讲义要求的完整能力包括：账号与权限、工单流转、AI 对话、FAQ/RAG 知识库、坐席/数据统计等。当前每日快照已完成“后端业务基础 + 认证授权 + 前端工单页面”的骨架，尚未形成端到端稳定闭环，更未接入真正的大模型。

### 1.1 五章讲义的知识地图

| 讲义 | 课程重点 | 对应当前项目 |
| --- | --- | --- |
| 第 1 章《实训项目需求》 | 项目角色、工单全流程、FAQ/RAG、AI 转人工、坐席和统计 | 定义系统最终范围与验收方向 |

| 第 3 章《SpringBoot3 集成 Sa-Token 权限框架》 | 登录/登出、Token、RBAC、权限注解、全局拦截、认证异常 | 7-21 后端认证授权 |
| 第 4 章《Web 框架 VUE3》 | Node/NPM、Vue 3 Composition API、组件通信、路由、Axios、Element Plus、Pinia 持久化、ECharts | 7-22 至 7-24 前端 |

### 1.2 当前系统的分层

```text
Vue 3 + Element Plus + Pinia + Axios
                │  /api 代理 + Bearer Token
Spring Boot 3 + Sa-Token + Validation + MyBatis-Plus
                │
              MySQL: ticket_system
```

前端开发服务器已配置 `/api -> http://localhost:8080` 代理；后端令牌名为 `Authorization`，前缀为 `Bearer`。这是后续联调必须遵守的契约。

## 4. 联调前必须修复的问题（P0）

这些不是“优化项”，而是可能使 7-24 当前代码无法稳定联调的阻塞项。

1. **登录/创建工单的请求格式不一致。** 前端 Axios 默认发送 JSON；后端 `LoginController.login(LoginRequest)` 和 `TicketController.createTicket(TicketCreateRequest)` 均没有 `@RequestBody`，按 Spring MVC 默认方式更适合接收表单/查询参数。建议统一为 JSON：后端参数加 `@RequestBody`，前端保持 JSON；或前端对这两项改为 `application/x-www-form-urlencoded`。
2. **`@NotBlank` 不适用于 `Long`。** `TicketCreateRequest.ordersId` 和 `MessageRequest.ticketId` 应从 `@NotBlank` 改为 `@NotNull`，否则参数校验可能抛出类型不匹配异常。
3. **前端订单分页类型错误。** 后端返回 `Page<Orders>`，前端却声明为 `R<Orders>`，但页面读取 `res.data.records`。应改为 `R<Page<Orders>>`。
4. **详情跳转和 ID 类型不一致。** 列表函数参数声明为 `TicketVo`，模板传入的是 `row.id`；详情接口函数要求 `number`，路由参数实际是字符串。应统一用 `ticketId: number`，并使用 `router.push({ name: 'detail', params: { id: row.id } })`。
5. **详情页的后续动作没有接入。** 发送消息、接单、解决、关闭、AI 反馈仍只有按钮和提示，需要补齐消息/更新工单 API。
6. **路由与菜单不完整。** `/home/orders`、`/home/policies`、`/home/chat` 已出现在菜单，却没有路由或页面；首页“订单管理”还跳到错误的 `/main/orders`。
7. **前端路由守卫缺失。** Token 持久化后仍可直接访问 `/home`；应在 `router.beforeEach` 中拦截未登录访问，并处理 401 后清空本地状态、跳回登录页。
8. **构建验证未通过。** 对 7-24 执行 `npm run build` 时，因该目录未安装依赖，报错 `run-p is not recognized`。先在该目录执行 `npm install`，再完成类型检查与生产构建；当前不能把“可运行”作为已验证结论。

## 7. 建议的验收顺序

1. 先修复 P0，完成一次前端 `npm run build` 和后端接口测试。
2. 用 `user_wang` 创建工单，确认只能看到自己的工单。
3. 用 `agent_zhang` 查看人工复核工单、回复并更新状态。
4. 用 `admin` 验证全量查看与管理权限。
5. 再接入 AI 普通对话；稳定后再做流式回复、Tool Calling、FAQ/RAG 和统计看板。

这样可以避免一开始就做大模型页面，却没有可靠的账号、工单、消息和权限数据基础。
